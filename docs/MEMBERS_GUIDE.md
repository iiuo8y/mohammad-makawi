## 0) الكل لازم يفهم هذه الصفحة أولاً (دقيقتان)

### الفكرة بجملة واحدة
عندنا عدة عمليات (processes) جاهزة ومعالج واحد فقط. **المجدول (CPU scheduler)** يقرر مين يشتغل بعدها. برنامجنا يأخذ العمليات، يطبق الخوارزمية، يرسم **Gantt chart** ويحسب الأرقام.

### رحلة البيانات داخل البرنامج (حفظها مهم — كل عضو يذكرها بجملة)

```
المستخدم يُدخل العمليات  ──►  gui.py
                                │  يضغط Run
                                ▼
                         core.run("SJF", processes, options)      ← العضو 1
                                │  يختار الخوارزمية من جدول ALGORITHMS
                                ▼
                 sjf.schedule(processes, options)                 ← صاحب الخوارزمية
                                │  تستخدم Dispatcher لبناء الخط الزمني
                                ▼
                         ScheduleResult (timeline)                ← models.py
                                │
                                ▼
                         metrics.compute(result)                  ← العضو 4
                                │
                                ▼
           gui.py يرسم الـ Gantt المتحرك + جدول النتائج           ← العضو 5
```

### القاعدة الذهبية في التصميم
**كل ملف خوارزمية فيه نفس الدالة:** `schedule(processes, options)` وترجع `ScheduleResult`.
لذلك كل عضو بنى واختبر جزءه لوحده، والواجهة تتعامل مع كل الخوارزميات بنفس الطريقة.

### المثال الذي سيستخدمه الجميع (من صفحة 3 في المقترح)

| Process | Arrival | Burst | Priority |
|:-:|:-:|:-:|:-:|
| P1 | 0 | 5 | 2 |
| P2 | 1 | 3 | 1 |
| P3 | 2 | 1 | 3 |

| الخوارزمية | الترتيب | متوسط الانتظار |
|---|---|:-:|
| FCFS | P1 (0–5) → P2 (5–8) → P3 (8–9) | **3.33** |
| SJF | P1 (0–5) → P3 (5–6) → P2 (6–9) | **2.67** |
| SRTF | P1 → P2 → P3 → P2 → P1 (0,1,2,3,5,9) | **1.67** |
| Round Robin q=2 | P1 → P2 → P3 → P1 → P2 → P1 (0,2,4,5,7,8,9) | **3.33** |

### الملفات والأسطر
| الملف | الأسطر | ماذا فيها |

### سكربت الفيديو — المرحلة 2: SJF
1. "SJF: كل مرة يفضى المعالج، أختار من العمليات **اللي وصلت** صاحبة **أقصر burst**."
2. **(sjf.py سطر 28)** "`ready` = العمليات اللي وصلت ولسا ما اشتغلت — هذا الـ ready queue."
3. **(سطر 31–35)** "لو ما في أحد جاهز، المعالج idle لحد أقرب وصول."
4. **(سطر 38)** "`min` بالمفتاح `(burst, arrival)`: الأقصر أولاً، ولو تساووا الأقدم وصولاً."
5. **(سطر 41–44)** "تشتغل للآخر — non-preemptive."
6. **(عرض على المثال)** "عند t=0 فقط P1 وصلت فتشتغل لـ 5. عند 5 عندي P2(3) و P3(1) — P3 أقصر. الترتيب P1, P3, P2 والمتوسط **2.67** أفضل من FCFS."
7. "SJF يعطي **أقل متوسط انتظار ممكن** (optimal) — لكن مشكلته إنه في الواقع ما نعرف طول الـ burst مسبقاً، النظام يتوقعه بالـ exponential averaging."

### سكربت المرحلة 3: SRTF
1. "SRTF هو SJF بس **preemptive**: كل وحدة زمنية أعيد القرار."
2. **(srtf.py سطر 25)** "`remaining` = كم باقي لكل عملية."
3. **(سطر 40)** "أختار الأقل **remaining**. لو تساووا أفضّل اللي شغّالة حالياً عشان ما أعمل context switch بلا فائدة."
4. **(سطر 43–47)** "أشغّلها **وحدة زمنية واحدة فقط** ثم أرجع أقرر — هذا اللي يخليها preemptive."
5. **(عرض)** "t=1 وصلت P2 تحتاج 3 < الباقي من P1 (4) ← تقاطعها. t=2 وصلت P3 تحتاج 1 ← تقاطع P2. المتوسط **1.67** — الأفضل بالثلاثة."
6. "لاحظوا عدد الـ context switches صار 4 — هذا ثمن المقاطعة."

### أسئلة متوقعة
- **الفرق بين SJF و SRTF؟** SJF ما يقاطع؛ SRTF يقاطع إذا وصلت عملية الباقي لها أقل.
- **وش عيب SRTF؟** ممكن **starvation** للعمليات الطويلة + context switches كثيرة.
- **ليش تشغلها وحدة وحدة؟** لأن القرار لازم يتراجع عند كل وصول جديد؛ أبسط طريقة صحيحة إنّا نقرر كل وحدة زمنية، و`Dispatcher` يدمج الوحدات المتتالية في مستطيل واحد.

### سكربت الفيديو — المرحلة 2: Round Robin
1. "Round Robin = **time sharing**: كل عملية تاخذ شريحة زمنية ثابتة اسمها **quantum**، لو ما خلصت ترجع لآخر الطابور."
2. **(round_robin.py سطر 30)** "الـ ready queue هنا `deque` — طابور حقيقي FIFO."
3. **(سطر 33–36)** "`admit_arrivals` تدخّل للطابور كل عملية وصلت لحد الوقت الحالي."
4. **(سطر 46)** "آخذ العملية من **أول** الطابور."
5. **(سطر 50–53)** "تشتغل `min(quantum, remaining)` — يعني quantum كامل أو أقل لو بتخلص."
6. **(سطر 55–58)** "مهم: العمليات الجديدة تدخل الطابور **قبل** العملية اللي انقطعت، ثم العملية المنقطعة ترجع للآخر."
7. **(عرض q=2 على المثال)** "P1 0–2، P2 2–4، P3 4–5، P1 5–7، P2 7–8، P1 8–9. متوسط الانتظار 3.33."
8. **(عرض مثال الكتاب)** `samples/textbook_rr.csv` مع q=4 ← المتوسط **5.67** مثل الكتاب.

### سكربت المرحلة 3: Context switch + المقارنة
1. **(dispatcher.py سطر 26–39)** "كل الخوارزميات تعطي المعالج عن طريق `dispatch`. لو العملية الجديدة **مختلفة** عن اللي قبلها، هذا **context switch**: النظام يحفظ حالة القديمة في الـ PCB ويحمّل الجديدة."
2. **(سطر 33–37)** "أعدّه، ولو `switch_cost > 0` أضيف مستطيل رمادي **CS** وأأخر بداية العملية. هذا الـ **dispatcher latency**."
3. **(سطر 61–68)** "لو نفس العملية تكمل، أطوّل المستطيل بدل ما أرسم مستطيلات صغيرة."
4. **(عرض)** SRTF على المثال مع switch cost = 1: "الوقت الكلي صار 13 بدل 9، و CPU utilization نزل إلى 69% — 4 وحدات ضاعت في التبديل."
5. **(compare.py سطر 13)** "`compare_all` تشغّل الخمس خوارزميات على **نفس** العمليات — هذا اسمه **deterministic modeling** في الكتاب."
6. **(عرض)** اضغط **Compare all** ← 4 رسوم: انتظار، turnaround، response، عدد التبديلات. الأفضل محاط بإطار أسود، والجدول يعلّم الفائز بـ ★.
7. "لاحظوا: RR أسوأ في الانتظار لكن **أفضل في response time** — مناسب للأنظمة التفاعلية."

### أسئلة متوقعة
- **وش يصير لو الـ quantum كبير جداً؟** يصير مثل FCFS.
- **ولو صغير جداً؟** context switches كثيرة جداً والوقت يضيع بالتبديل. القاعدة: 80% من الـ bursts أقصر من الـ quantum.
- **أول عملية تحمّلها تنحسب context switch؟** لا، أول تحميل ما ينحسب؛ كل تبديل بين عمليتين مختلفتين ينحسب.

### سكربت الفيديو — المرحلة 2: Priority + المقاييس
1. "في Priority scheduling العملية الأهم تشتغل أول. عندنا مثل الكتاب: **الرقم الأصغر = أولوية أعلى**."
2. **(priority.py سطر 48–50)** "في الوضع non-preemptive، العملية الشغالة تكمل لحد ما تخلص."
3. **(سطر 53)** "غير كذا أختار أصغر رقم أولوية؛ لو تساووا أفضّل الشغالة ثم الأقدم وصولاً."
4. **(عرض مثال الكتاب)** `samples/textbook_priority.csv`: "الترتيب P2, P5, P1, P3, P4 والمتوسط **8.2** — نفس الكتاب."
5. **(metrics.py سطر 52–58)** "من الـ timeline آخذ لكل عملية **آخر مستطيل** = completion و**أول مستطيل** = أول تشغيل، وبعدها:"
   - **Turnaround = Completion − Arrival**
   - **Waiting = Turnaround − Burst**
   - **Response = First run − Arrival**
6. **(سطر 64، 71–72)** "**CPU utilization** = وقت الشغل المفيد ÷ الوقت الكلي (بدون idle و CS). **Throughput** = عدد العمليات ÷ الوقت الكلي."
7. **(تحقق يدوي على SRTF)** P1: 9−0=9، 9−5=**4** · P2: 5−1=4، 4−3=**1** · P3: 3−2=1، 1−1=**0** ← (4+1+0)/3 = **1.67** ✔

### سكربت المرحلة 3: Preemptive + Aging
1. **(عرض)** "فعّلوا Preemptive: مثال P1(0,5,pr3) و P2(2,2,pr1) ← P2 أهم فتقاطع P1 عند t=2: P1 0–2، P2 2–4، P1 4–7."
2. "المشكلة: **Starvation** — عملية أولويتها منخفضة ممكن تنتظر للأبد إذا العمليات المهمة ما وقفت."
3. **(سطر 65–73)** "الحل **Aging**: كل `aging_interval` وحدة تنتظرها العملية، رقم أولويتها ينقص 1 (تصير أهم) لحد الصفر. كل ما انتظرت أكثر صارت أهم — فما تنتظر للأبد."
4. **(عرض)** `samples/starvation.csv`: "بدون aging: P3 (أولوية 5) تخلص آخر شي عند **23**. مع aging كل 2: تشتغل عند 12 وتخلص عند **15**."

### أسئلة متوقعة
- **الفرق بين waiting و response؟** waiting = مجموع كل وقت الانتظار؛ response = حتى **أول** مرة اشتغلت فقط. في non-preemptive هم متساويين.
- **ليش Waiting = Turnaround − Burst؟** لأن وقت العملية في النظام = وقت شغلها + وقت انتظارها (وتشمل وقت الـ context switch).
- **مين يحدد الأولوية في الحقيقة؟** داخلياً (ذاكرة، I/O…) أو خارجياً (أهمية المستخدم/المهمة).

### أسئلة متوقعة
